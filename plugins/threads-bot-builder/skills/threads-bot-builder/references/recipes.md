# Threads bot 案例與填寫方式

案例是校準，不是型態清單。執行 Agent 應把使用者答案填入相同欄位，再自行補完
來源 adapter、資料模型與部署方式。

## 空白決策卡

| 欄位 | 要回答的問題 |
|---|---|
| 目標 | 這個帳號要替誰省下哪段重複勞動？ |
| 來源 | 原始素材從哪裡來，使用權與 freshness 怎麼判斷？ |
| 觸發 | 固定時段、事件、webhook，或人工啟動？ |
| 去重鍵 | 哪個穩定業務鍵可證明「同一件事」？ |
| 人工 gate | 使用者在哪一步看到什麼，如何批准或跳過？ |
| 紅線 | 哪些主題、語氣、推廣或回覆必須停？ |

## 原作者實跑案例：GitHub 專案策展

這是作者實際運作過的版本，可信價值在已踩過的故障，不代表推薦所有人照做。

| 欄位 | 決策 |
|---|---|
| 目標 | 每天替讀者挑一個仍在維護、值得研究的開源專案 |
| 來源 | GitHub Trending 或 Search API |
| 觸發 | 每天 20:00 Asia/Taipei |
| 去重鍵 | repo 全名，比對近 30 天 |
| 人工 gate | 使用者先選方向或跳過，再產生草稿 |
| 選材 | 維護活躍、有明確用途；排除清單型與疑似灌星 |
| 語氣 | 第一人稱、最多一個 emoji、保留平台字數 buffer |

已驗證的教訓：

1. 同一素材連跑兩次必須在發布前被擋下。
2. create 成功不代表 publish 成功；兩者 id 與錯誤要分開記。
3. 固定等待秒數不能證明 container ready。
4. token 或排程失效若沒有告警，外觀只會是「某天突然不發」。
5. Windows 中文需以 UTF-8 round-trip 驗證，不能只看本機終端顯示。

換成存稿、產品更新或互動回覆時，只沿用決策卡與 gates；實作細節由 Agent
依資料來源、風險與現有 repo 補完。
