# Threads 發文 bot 建造器(threads-bot-builder)

## 什麼時候用

- 使用者想固定在 Threads 產出內容,但每次手挑手寫太耗時
- 使用者想做排程發文或發文 bot,但不想要「全自動亂發」砸帳號
- 使用者要接 Threads API,想避開憑證、編碼與 token 的已知陷阱

不適用:使用者想做「完全無人值守、AI 自己決定發什麼」的全自動 bot ——
這份 SOP 的立場正好相反,見下方架構總覽。

## 第 -1 步:先問他要做哪一種(不要跳過這步)

**這一步決定後面三步怎麼寫,不要預設他要做哪一種。**

同一套骨架能做出很不一樣的 bot。差別只在四個欄位:內容從哪來、多久發
一次、拿什麼當去重鍵、這一型最容易做歪的地方。骨架完全一樣。

用 AskUserQuestion 問,選項可以照下表,也可以依他的狀況改寫:

| 型態 | 內容從哪來 | 頻率 | 去重鍵 | 這一型最容易做歪的地方 |
|---|---|---|---|---|
| **內容策展** | 你關注的來源(專案、論文、新品、他人貼文) | 每天 1 篇 | 來源項目的唯一 ID | 變成無腦轉貼,沒有自己的觀點 |
| **新聞快訊** | RSS / 新聞 API | 事件驅動,有大事才發 | 標題 + 原文網址 | 沒大事硬發,帳號變雜訊 |
| **存稿排程** | 使用者自己先寫好的稿池 | 固定時段 | 稿件 ID | 稿池見底後空轉或重複發 |
| **長內容改寫** | 使用者自己的文章 / 電子報 / 影片 | 每篇長文發布後 | 原文網址 | 一稿切太多則,變洗版 |
| **產品 / 專案動態** | changelog、release、里程碑 | 有更新才發 | 版本號 | 全是宣傳,沒人想追蹤 |
| **互動回應** | 收到的留言、提問、提及 | 觸發式 | 留言 / 訊息 ID(不是對話 ID,不然同一串的第二則會被誤擋) | 自動回覆變罐頭,比不回更傷 |

還有一個選項一定要留:**「以上都不是,我想做的是……」**。這份骨架不預設
用途,他講得出來就照他的做,把他的答案填進上表那四個欄位即可。

問完把答案寫成一行,例如:

> 型態:長內容改寫|來源:我的電子報 RSS|頻率:每期發布後隔天|
> 去重鍵:原文網址|要小心:一期最多切 2 則

這一行是後面所有步驟的依據,寫進第 2 步的流程指引檔。

## 架構總覽(人在迴路)

核心不是「全自動」,是「**人出方向,AI 包勞動**」:

1. 固定時間(或事件觸發)由排程叫醒 bot
2. 觸發後第一件事**不是發文**,是問使用者一題(今天走哪個方向?
   或直接給他看選好的素材讓他點頭)
3. 使用者點一下之後,選材、去重、寫文、發文全部自動
4. 使用者出 5 秒判斷,省下每次二十幾分鐘的重複勞動;而且每篇都是他
   看過方向的,不會發出他沒同意的東西

為什麼堅持人在迴路:全自動發文很容易吐出一堆機器味、沒人看過的內容,
反過來砸掉帳號可信度。自動化可以省力,但不能拿可信度去換。

引導時先確認他接受這個架構再動工。**若他堅持全自動,提醒風險後尊重
決定** —— 但至少幫他留一個「發文前寫進草稿檔、隔 N 分鐘才真發」的
緩衝,讓他有機會攔截。

## 照步驟做

動工前先跑第 0 步,之後每完成一步先跟使用者確認再往下。

### 第 0 步:確認環境

先問清楚,不要假設:

- 作業系統(Windows 使用者要特別注意第 6 步的編碼坑)
- 排程要用什麼(Claude Code 的 scheduled-tasks、系統排程器、cron、
  雲端排程服務都可以;問他機器會不會一直開著)
- 要用哪個 Threads 帳號發文
- 型態專屬的前置(例如:存稿排程要先有稿池、長文改寫要先有 RSS)

### 第 0.5 步:開瀏覽器,陪他把 Threads 憑證拿到手

**這是最多人放棄的地方。不要只丟一句「去 Meta 開發者後台申請」。**

各家後台改版很勤,任何寫死的點擊步驟過幾個月就對不上。所以這份文件只
定義「要拿到什麼」和「怎麼確認拿對了」,實際畫面由你當場開瀏覽器看著辦。

**先確認你有沒有瀏覽器能力**

1. 有瀏覽器工具(能開網頁、讀畫面、點選)→ 直接用。
2. 沒有 → 先花三分鐘讓他裝起來,這比讓他自己摸索後台省事得多:
   引導他安裝 **Claude 的 Chrome 擴充功能**(Chrome 線上應用程式商店
   搜尋 Claude)。**先確認他符合條件再叫他去裝**:需要付費方案、只支援
   正牌 Chrome(Edge、Brave、Arc 這些分支不支援),且仍在 beta。
   裝完帶他實驗一次確認通了 —— 這個工具他之後做別的事也用得到。
3. 兩者都沒有 → 退回口述模式:一次只講一步,每步問他「畫面上看到什麼」,
   用他的回答決定下一句怎麼講。不要一次倒十個步驟給他。

**陪跑的規矩(這幾條不能破)**

- **帳號、密碼、驗證碼一律他自己打。** 你不代填、不代讀。
- **送出、同意條款、建立應用程式、產生金鑰這類按鈕,由他按。**
- **拿到的 token 不要貼進對話。** 請他直接貼進 `.env`,你只看驗證指令的輸出。
- **叫他不要截整個畫面貼給你** —— App Secret 就在那個畫面上。要看的話
  請他先遮住,或改成用文字描述看到哪些選項。
- **卡住的出口**:同一步試三次還找不到按鈕就不要繼續猜。改成請他描述
  整個畫面有哪些字、去查官方文件看現在的畫面長怎樣。
  **不要讓他在同一個畫面卡超過十分鐘**,那是多數人放棄的地方。

**要達成的狀態**(照順序,每項達成再往下)

1. 有一個 Threads 帳號可以用來發文。
2. 在 Meta 的開發者後台建好應用程式,加入 Threads 相關產品。
3. 權限**依型態勾**,不要一律照抄:

   | 你要做什麼 | 要勾的權限 |
   |---|---|
   | 只發文(多數型態) | `threads_basic` + `threads_content_publish` |
   | 互動回應型(要讀留言、要回覆) | 再加 `threads_manage_replies` |
   | bot 要能刪自己發的文 | 再加 `threads_delete` |

   **自用不必送 App Review**,要開放給別人用才需要 —— 先講,免得他
   以為要等審核。權限名稱以官方文件當下為準。
4. 走完授權流程拿到 token,並**換成長期 token**(短期的很快過期)。
5. 拿到自己的 Threads 使用者 ID(發文端點要用)。

**驗證拿對了**(這條由他在終端機跑,你看輸出。不要叫他把帶 token 的
網址貼進瀏覽器 —— 會留在歷史紀錄裡):

```bash
curl -s "https://graph.threads.net/v1.0/me?fields=id,username&access_token=$THREADS_TOKEN"
```

回傳裡有他的帳號名就代表憑證正確。**沒過就停在這裡把它弄對,不要往下走**
—— 不然後面每一步都會失敗,而且錯誤訊息看起來跟 token 完全不相干。

> 上面的網址與參數以 Meta 官方文件為準。後台畫面會改版、API 也會升版本,
> 對不上的時候以你當場在官方文件看到的為準,不要硬套這份文件。

### 第 1 步:排程設定

依第 -1 步選的頻率設定觸發:

- 固定時段(存稿排程、內容策展)→ 每天固定時間跑一次
- 事件驅動(新聞快訊、產品動態)→ 每 N 分鐘掃一次來源,有夠格的才發
- 觸發式(互動回應、長文改寫)→ 由 webhook 或發布事件觸發

時間與時區依他的作息調。**問清楚他的機器會不會一直開著** —— 自己的
電腦關機就停,長期跑要放常開的機器或雲端排程服務。

### 第 2 步:建立流程指引檔

把完整流程寫成一份指引檔,排程觸發時照這份跑:

> 問方向 → 選材 → 去重 → 寫文 → 發文 → 記 log

**第 -1 步那一行(型態/來源/頻率/去重鍵/要小心的地方)、語氣規則、
紅線,全部寫死在這份指引檔裡**,不要每次重講一遍。

### 第 3 步:問方向(依型態不同)

觸發後第一步問使用者一題。問法依型態:

- **內容策展 / 新聞快訊** → 問今天想看哪個方向(選項用他平常關注的領域)
- **存稿排程** → 把稿池裡排最前面那篇的摘要給他看,問「發這篇嗎」
- **長內容改寫** → 問這次要主打原文的哪個角度
- **互動回應** → 把收到的訊息與擬好的回覆一起給他看,問「這樣回嗎」

不管哪一型,**「今天跳過」都必須是合法選項** —— 人在迴路的意思是人
隨時可以喊停。

### 第 4 步:選材 + 去重(依型態不同)

這一步是「決定這次要講什麼」。來源照第 -1 步的答案接:

| 型態 | 怎麼拿到候選 | 怎麼挑 |
|---|---|---|
| 內容策展 | 來源站的 API 或搜尋頁 | 挑熱度高、且最近仍在更新的;避開清單型與明顯灌水的 |
| 新聞快訊 | RSS / 新聞 API | 用一個便宜的模型批次評重要性分數,只有過閾值的才進下一步 |
| 存稿排程 | 讀稿池檔案或資料庫 | 照順序或依標記的優先度 |
| 長內容改寫 | 抓自己文章的 RSS / sitemap | 挑最新一篇,拆出 2-3 個可獨立成立的點 |
| 產品動態 | release API / changelog | 只挑使用者有感的變更,不是每個 commit 都值得發 |
| 互動回應 | 平台的通知 / 提及 API | 先過濾掉不需要回的(廣告、單純表情) |

**去重是這一步的重點,不是選配。** 拿第 -1 步定的去重鍵比對過去 N 天的
發文 log,發過的不要再發。這是自動發文最容易翻車的地方 —— 重複發同一
件事,追蹤者一眼就看出是機器在跑。

去重的資料來源就是第 8 步的 log,所以那步不能省。

### 第 5 步:依語氣規則寫文(依使用者定義)

**存稿排程型可以整步跳過** —— 稿子已經寫好了,這步是空的,不要硬套。
長內容改寫型也只需要「切分 + 潤成適合這個平台的長度」,不是重寫。

**其他型態:不要用預設語氣,引導他定義自己的。** 一組語氣規則長這樣
(這是原作者自己的版本,當範例不要當標準):

- 第一人稱
- 整篇最多 1 個 emoji
- 句尾不加句號,直接換行
- 控制在 480 字以內(Threads 上限 500,留 buffer)

問他:平常怎麼寫?有沒有不想用的詞?要不要 emoji?
把答案寫進流程指引檔,不要每次重問。

如果他已經有語氣檔或過去的貼文,直接拿來當範例讓 AI 對齊,比口頭描述準。

### 第 6 步:兩段式發文

Threads API **不是一步發**,是兩段式:

1. 先建一個 `media_type` 為 `TEXT` 的 container
2. sleep 約 2 秒(不等的話 container 還沒就緒,publish 會失敗)
3. 再 publish

示意(端點與參數以 Meta 官方文件為準):

```bash
# 1. 貼文先寫成 UTF-8 檔(Windows 必要,原因見下方踩坑)
#    post.txt 內容 = 貼文全文

# 2. create container
CONTAINER_ID=$(curl -s -X POST "https://graph.threads.net/v1.0/<YOUR_THREADS_USER_ID>/threads" \
  --data-urlencode "media_type=TEXT" \
  --data-urlencode "text@$(cygpath -m /path/to/post.txt)" \
  --data-urlencode "access_token=$THREADS_TOKEN" | jq -r '.id')

# 3. sleep 再 publish
sleep 2
curl -s -X POST "https://graph.threads.net/v1.0/<YOUR_THREADS_USER_ID>/threads_publish" \
  --data-urlencode "creation_id=$CONTAINER_ID" \
  --data-urlencode "access_token=$THREADS_TOKEN"
```

**回覆別人的貼文、或把一篇長內容切成串文**(互動回應型與長內容改寫型
會用到):做法一樣是「建 container → publish」,差別只在建 container 時
要多帶一個參數指明要回覆哪一篇。

**這個參數名我不寫在這裡,請你當場去查官方文件的 Reply 章節** ——
寫死在教學裡的參數名最容易過期,而且錯一個字整個功能就不會動。
你需要的線索:權限要 `threads_manage_replies`(見第 0.5 步),
串文的做法是「發第一則 → 拿到它的 ID → 第二則回覆第一則」,依此類推。

先用一則測試貼文把回覆跑通,再接進自動流程。

token 一律走環境變數或機密管理工具注入,不硬編碼進腳本、不寫進會 commit
的檔案。順手建 `.env.example`(只放欄位名不放值),把 `.env` 寫進
`.gitignore`,並**幫他確認真的被 ignore 了**(`git check-ignore -v .env`
有輸出就對了)。

> `.env` 不會自己生效。程式要主動載入它(Python 用 `python-dotenv` 的
> `load_dotenv()`),否則 key 明明貼進去了卻讀不到,看起來像 token 拿錯。

### 第 7 步:token 自動 refresh

長期 token 大約 **60 天會靜默失效** —— API 其實有回錯,但如果程式沒有
把發文失敗記下來、沒有通知他,從外面看就是某天默默不發了。對策:

- 建一個 refresh 腳本(token 滿 24 小時後即可刷新),排每週自動跑一次
- 刷新後的新 token 要回寫到 bot 讀取的位置
- **發文失敗一定要留紀錄並告警**,不然壞掉他不會知道

### 第 8 步:每步記 log

「沒報錯但也沒發」是這類 bot 最難抓的故障型態。流程每一步(選材結果、
去重判斷、產出的文、container id、publish 回應)都要記 log,方便事後
對照哪一步斷掉。log 同時是第 4 步去重的資料來源。

### 第 9 步:先 dry-run,確認再開真發

**做一個 dry-run 模式**:照跑選材、去重、寫文,但不真的發 —— 貼文存成
草稿檔,他先看過再開真發。前兩週建議全 dry-run。另外做一個 `--force`
方便測試。

**四個檢查點,過了才算做完:**

1. `curl .../me` 回傳他的帳號名 → 憑證對了
2. dry-run 跑完,草稿檔裡有一篇讀起來像人寫的文 → 產線通了
3. 去重測試:同一個素材連跑兩次,第二次應該被擋下來 → 去重通了
4. 關掉 dry-run 發第一篇,Threads 上真的看得到 → 全線通了

第 3 點特別容易被跳過,而它是實際跑起來最先出問題的地方。

## 原作者實跑過的版本(範例 recipe)

以下是這份 SOP 的原始出處:一個**內容策展**型的 bot,策展 GitHub 上的
好專案,每天 20:00 發一篇。**這是作者自己實際在跑的版本**,不是示範用的
假設案例 —— 上面所有的坑都是從這個版本踩出來的。

拿它當填法的參考,不要當成使用者一定要做的東西:

| 欄位 | 這個版本的答案 |
|---|---|
| 型態 | 內容策展 |
| 內容從哪來 | 選「隨意挑」→ 抓 GitHub trending;指定方向 → 走 GitHub search 按 star 排序抓前 15 個 |
| 頻率 | 每天 20:00(Asia/Taipei)一篇 |
| 去重鍵 | repo 全名,比對過去 30 天的發文 log |
| 挑選規則 | 高 star、最近仍有維護;避開 awesome-list 類清單與明顯刷 star 的 |
| 第 3 步的選項 | AI / agent、CLI 工具、全端後台、隨意挑、今天跳過 |
| 語氣規則 | 第一人稱、最多 1 個 emoji、句尾不加句號、480 字以內 |

換成別的型態時,骨架一行都不用改,只有上面這張表的內容不同。

## 我踩過的坑(原作者實測)

1. **Windows CP950 編碼**:Git Bash 的 curl 是 Windows 原生 build,中文
   直接塞進命令列會被 CP950 codepage 轉成亂碼。解法:貼文先用 Write 寫成
   UTF-8 檔,curl 用 `--data-urlencode` 搭配 `@檔案` 讀,路徑用
   `cygpath -m` 轉成 curl 讀得懂的格式。
2. **兩段式發文的時序**:create container 後直接 publish 會失敗,
   中間要 sleep(約 2 秒)。
3. **token 60 天靜默失效**:不會主動報錯給你看,就是某天開始不發了。
   每週自動 refresh + 每步 log 是唯二保險。
4. **「沒報錯但也沒發」**:這種靜默故障最難 debug,所以 log 不是選配。

## 紅線與注意

### 通用紅線(不管做哪一型都守)

1. **不超過 500 字**:Threads 上限,寫文時留 buffer 控在 480 內
2. **不堆 hashtag、不重複發同一件事**
3. **推廣要誠實標示**:有商業關係的內容(業配、聯盟、自家產品)就明講,
   不要混在看起來像純分享的貼文裡。**這條跟「能不能放推廣」無關,
   是「有沒有講清楚」** —— 做產品動態、商品導購型的人照樣可以放連結,
   但要讓人看得出來那是推廣。

### 依型態自己定的紅線

**帶使用者定一次,寫進流程指引檔。** 不同型態的紅線差很多:

| 型態 | 通常要守的 |
|---|---|
| 內容策展 | 不塞 CTA、不放聯盟連結 —— 策展帳號的價值是「這個人真的在看這些」,順手塞推廣可信度就崩了 |
| 產品動態 / 導購 | 可以放連結與 UTM,但要標示;不要每篇都在賣,留給讀者有用的東西 |
| 新聞快訊 | 不改寫成聳動標題、不下自己沒查證的結論 |
| 互動回應 | 回覆要看得出是人在回;有爭議的問題不要自動回,轉給本人 |
| 涉及金融、醫療、法律 | 不給個人化建議、不保證結果 —— 這類主題的自動化風險最高,先確認他知道 |

原因:bot 最容易做歪的地方就是「順手塞」。**先讓使用者自己講出他這個
帳號的紅線是什麼**,寫死進指引檔,比你替他決定有用。

另外幾條:

- Threads API 是官方 API,正常使用不會被鎖帳號;有發文 rate limit
  (原作者當時實測約每天 250 篇 publish,**以官方文件當下的數字為準**),
  日發 1-2 篇遠低於上限
- 不堆 hashtag、不重複發同一件事
- **想換平台(X / Bluesky / Mastodon)**:第 -1 到第 5 步完全通用,
  只有第 6 步的發文 API 要換。所以把發文那段做成最後一段獨立 function,
  換平台時只動那一個檔案
- **如果做的是互動回應型**,多守一條:回覆要能看出是這個帳號的人在回,
  不是罐頭。自動回覆做不好比不回還傷
