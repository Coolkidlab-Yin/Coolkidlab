# LINE bot 建造器(line-bot-builder)

## 什麼時候用

- 想做任何活在 LINE 裡的 bot:客服、預約、提醒、打卡、通知、小工具
- 想學 LINE Messaging API 的 webhook 收訊息 / push 完整接法
- 在猶豫「這個 bot 到底要不要接 LLM」
- 卡在 channel token 申請、webhook 驗證一直失敗
- 想知道 cron 定時推播怎麼不重複發

核心前提:**工具的死亡點是「要另外開一個 app」**。做在 LINE 裡的東西
不另開介面,直接活在使用者本來就整天掛著的地方 —— 這是 LINE bot 最大的
優勢,也是決定要不要做 LINE bot 的判準。

## 第 -1 步:先問他要做哪一種(不要跳過這步)

**這一步決定整個架構,不要預設他要做哪一種。**

同一套骨架能做出很不一樣的 bot。差別在五個欄位:誰在用、bot 回什麼、
要不要主動推播、資料存什麼、要不要接 LLM。骨架完全一樣。

用 AskUserQuestion 問,選項可以照下表,也可以依他的狀況改寫:

| 型態 | 誰在用 | bot 做什麼 | 主動推播 | 資料存什麼 | 要不要 LLM |
|---|---|---|---|---|---|
| **客服 / 常見問答** | 你的顧客 | 回答問題,答不出來轉真人 | 少(只有主動通知) | 問答紀錄、未解決的問題 | **要**,但要接你自己的資料 |
| **預約 / 報名** | 顧客 | 引導填時段、留資料、確認 | 要(提醒 + 變更通知) | 預約單、時段、顧客資料(**含個資**) | 不用,狀態機就夠 |
| **行程 / 待辦提醒** | 你自己或家人 | 建行程、到點提醒 | **要,這是主功能** | 行程、參加者、提醒狀態 | 不用 |
| **個人教練 / 打卡** | 你的學員 | 收紀錄、給回饋、追進度 | 要(每日提醒) | 每日紀錄、進度、目標 | 看回饋要多客製 |
| **通知推播** | 內部團隊 | 幾乎不收訊息,只負責發 | **只有這個** | 收件人清單、發送紀錄 | 不用 |
| **內部小工具** | 同事 | 查東西、觸發流程 | 看情況 | 通常不用存,直接查現有系統 | 通常不用 |

還有一個選項一定要留:**「以上都不是,我想做的是……」**。這份骨架不預設
用途,他講得出來就照他的做,把他的答案填進上表那五個欄位即可 ——
填完那五格,後面每一步要怎麼做就決定了。

問完把答案寫成一行,例如:

> 型態:客服問答|使用者:網站來的顧客|回什麼:產品規格與退換貨|
> 推播:只有訂單狀態變更|LLM:要,接自家 FAQ

這一行是後面所有決策的依據。

## 最重要的一個判斷:這個 bot 要不要接 LLM

**先做這個判斷再動工。接錯邊會浪費最多時間。**

| | 不接 LLM(keyword + 狀態機) | 接 LLM |
|---|---|---|
| 適合 | 指令集固定(建行程、查詢、報名、打卡) | 使用者會亂問、問法千變萬化(客服、問答) |
| 回應速度 | 即時 | 有延遲,要考慮 LINE 的回覆時限 |
| 行為 | 可預測,同樣輸入永遠同樣輸出 | 會自由發揮,長輩與不熟的人容易被搞糊塗 |
| 成本 | 零 API 成本 | 按用量計費 |
| 隱私 | 使用者輸入不出你的伺服器 | 輸入會送到第三方,**要先想清楚哪些內容會被送出去** |

**判斷「哪裡不用 AI」跟「哪裡用 AI」一樣重要。** 指令集固定的話,
keyword 比對 + 一句話規則解析就能 100% 搞定,不要為了用 AI 而用 AI。

折衷做法(推薦給大多數型態):**主流程走規則,LLM 只當 fallback** ——
規則抓不到才丟給模型。這樣常見情境即時又可預測,長尾情境也接得住。

## 照步驟做

### 元件清單(照這個順序建)

1. **webhook + LINE Messaging API**:收訊息 / push 的完整接法(見第 1 步)
2. **訊息路由**:keyword 比對 → 對話狀態機 → 規則解析 → fallback,
   照這個順序。決定 fallback 要不要丟 LLM(見上面那張表)
3. **對話狀態機**(需要多輪問答的型態才要):一步步問完必填欄位,
   草稿存資料庫,中途打「取消」隨時跳出
4. **資料層**:同一套 code 本機跑 SQLite、線上跑 Postgres,
   用 ORM + 自訂型別轉換抹平差異;schema 變更用 migration 工具管
5. **主動推播 + 去重**(要推播的型態才要,見第 3 步)
6. **onboarding**:使用者怎麼開始用?依型態不同 —— 客服型是加好友就能問,
   多人共用型要有邀請碼或群組綁定
7. **介面元件**(給真正的外部使用者用的型態要做):LINE 提供圖文選單、
   快速回覆按鈕、卡片式訊息這幾種互動元件。**客服與預約型幾乎一定要用**
   —— 純文字問答對顧客來說體感很差,選時段要用打字的沒人想用。
   自己人用的內部工具可以省。具體元件名稱與 JSON 格式當場查官方文件,
   格式會改版

不是每個型態都要全部七項。**通知推播型只要 4、5(連 webhook 都不用);
客服型要 1、2、4、7;預約型要 1、2、3、4、5、7。**
問清楚再決定要建哪幾個,不要照抄全套。

### 第 0 步:確認環境

先問清楚,不要假設:

- 程式語言與版本(下面的例子用 Python + FastAPI,換別的語言骨架一樣)
- 部署到哪裡(**webhook 必須是公開的 HTTPS 網址**,本機開發要用
  ngrok 之類的工具拿臨時網址)
- 資料庫用什麼(本機先 SQLite 跑通、上線再換雲端 Postgres 是低風險路線)
- 預期使用者數量與訊息量(影響免費額度夠不夠,見下方)

### 第 0.5 步:開瀏覽器,陪他把 LINE 憑證拿到手

**這是最多人放棄的地方。不要只丟一句「去 LINE Developers 申請」。**

後台改版很勤,任何寫死的點擊步驟過幾個月就對不上。所以這份文件只定義
「要拿到什麼」和「怎麼確認拿對了」,實際畫面由你當場開瀏覽器看著辦。

**先確認你有沒有瀏覽器能力**

1. 有瀏覽器工具 → 直接用。
2. 沒有 → 引導他安裝 **Claude 的 Chrome 擴充功能**(Chrome 線上應用程式
   商店搜尋 Claude)。**先確認他符合條件再叫他去裝**:需要付費方案、
   只支援正牌 Chrome(Edge、Brave、Arc 這些分支不支援),仍在 beta。
   裝完帶他實驗一次確認通了。
3. 兩者都沒有 → 退回口述模式:一次只講一步,每步問他「畫面上看到什麼」。

**陪跑的規矩(這幾條不能破)**

- **帳號、密碼、驗證碼一律他自己打。** 你不代填、不代讀。
- **送出、同意條款、建立 channel、發行 token 這類按鈕,由他按。**
- **拿到的 token 與 secret 不要貼進對話。** 請他直接貼進 `.env`,
  你只看驗證指令的輸出。
- **叫他不要截整個畫面貼給你** —— channel secret 就在那個畫面上。
- **卡住的出口**:同一步試三次還找不到按鈕就不要繼續猜,改成請他描述
  整個畫面有哪些字。不要讓他在同一個畫面卡超過十分鐘。

**要達成的狀態**(照順序)

1. 在 LINE Developers 主控台建好 Provider 與一個 **Messaging API** channel。
2. 拿到兩個東西:**Channel secret**(驗簽用)與 **Channel access token**
   (發訊息用,要發長期的那種)。兩個都進 `.env`。
3. **把自動回覆訊息與歡迎訊息關掉** —— 不關的話你的 bot 回什麼都會被
   官方的罐頭訊息蓋掉,而且新手完全看不出問題在哪。這條最常漏。
4. Webhook URL 填你部署好的公開 HTTPS 端點,並**打開 Use webhook**。
5. 按 **Verify**,顯示成功才算通過。

**第 4、5 項只有「要收訊息」的型態需要。** 純推播型(只發通知、不收
訊息)沒有 webhook 也能運作 —— 拿到 channel access token 就能 push。
別讓他為了一個用不到的端點去架伺服器。

**驗證拿對了**

- 要收訊息的型態:Verify 顯示成功,**而且**你手機加 bot 好友後隨便打
  一句話,伺服器的 log 有收到事件。兩個都要 —— 只有 Verify 過不代表
  訊息真的進得來。
- 純推播型:用 token 對自己的帳號 push 一則測試訊息,手機收得到就對了。

> 上面的名詞與流程以 LINE 官方文件為準。後台會改版,對不上的時候
> 以你當場看到的官方文件為準,不要硬套這份文件。

### 第 1 步:webhook 收訊息(所有型態都要)

三件事一定要做對:

1. **驗簽**:LINE 送來的每個請求都帶一個簽章 header,要用 channel secret
   對**原始 request body**(不是解析後的物件)做 HMAC-SHA256 再比對。
   **不驗簽等於任何人都能偽造訊息打你的 bot。** 這不是選配。
2. **快速回 200**:LINE 對 webhook 有回應時限,處理太久會被判失敗。
   耗時的工作(呼叫 LLM、寫外部 API)要丟到背景,先回 200。
3. **reply 與 push 的差別**:回覆使用者剛剛的訊息用 reply(不計入推播
   額度);主動發訊息用 push(**會計入額度**,見下方)。

### 第 2 步:訊息路由

順序固定:**keyword 比對 → 對話狀態機 → 規則解析 → fallback**。

先比對明確的指令(「查詢」「取消」「說明」),再看這個使用者是不是正在
某個多輪流程中間,再試規則解析,都不中才走 fallback。

fallback 要做什麼依第 -1 步的判斷:回一句「我不太懂,你可以試試……」
就夠的話不用接 LLM;要能接住自由問法才需要。

### 第 3 步:主動推播 + 去重(要推播的型態才做)

推播的典型做法:一個外部排程每分鐘打你的派送端點,端點撈出「該發但還
沒發」的項目,發完標記。

**三個必踩的坑,先講先避開:**

1. **派送端點一定要驗 secret header**,不然裸奔在公開網路上,誰都能打。
2. **發完要立刻標記已發送**,不然下一分鐘又撈到同一筆,使用者被連環轟炸。
3. **部分失敗不要重試整筆**:發給三個人其中一個失敗,只記 log,
   不要整筆重跑 —— 重試會害已經收到的人再收一次。寧可漏記一個,
   也不要讓人被疲勞轟炸。

### 第 4 步:資料層

本機用 SQLite、線上用 Postgres,同一套程式碼。用 ORM 加自訂型別轉換
抹平兩邊在 UUID / JSON 欄位上的差異,schema 變更用 migration 工具管。

好處是「本機測完直接上線」不會踩資料庫差異的雷。不想為了測一個小功能
就連雲端資料庫,這個安排值得。

### 第 5 步:先在自己身上跑通,再給別人用

**檢查點,過了才算做完:**

1. LINE 後台按 Verify → 顯示成功(webhook 通了,**純推播型跳過**)
2. 手機加 bot 好友、打一句話 → bot 有正確回應(路由通了,**純推播型跳過**)
3. 用 curl 帶 secret header 打派送端點 → 回傳有發出幾筆,
   而且手機真的收到(推播通了,**沒做推播的型態跳過**)
4. **重複觸發測試**:同一筆推播讓排程連跑兩次,第二次不該再發一次
   (去重通了)
5. 找一個真實使用者試用一次,他不用問你就會用(可用性通了)

第 4 點特別容易被跳過,而它是實際跑起來最先出問題的地方。

## 錢與額度(先講,不然會撞牆)

- **LINE 的推播訊息有月額度上限**,免費方案的額度不多,超過要升方案;
  回覆使用者的 reply 訊息通常不計入。**主功能是主動推播的型態
  (提醒、通知、教練打卡)最容易撞到** —— 使用者數 × 每天推播次數
  先算一次再決定架構。
- 免費的資料庫與部署平台通常有休眠機制,冷啟動要數十秒;靠外部定時
  ping 可以保活,但不適合對延遲極敏感的場景。
- **以上額度與條件以各服務官方當下的方案頁為準**,會變動。

## 原作者實跑過的版本(範例 recipe)

以下是這份 SOP 的原始出處:一個**家族共享行程提醒**bot。家人在 LINE 打
一句「明天下午 3 點 <家人稱呼> 醫院回診 提前 1 小時提醒」,bot 用規則
解析出時間 / 對象 / 事由 / 提前量存進資料庫,一個 cron 每分鐘撈出到點
未通知的行程 push 給相關的人。

**這是作者自己家裡實際在用的版本** —— 上面所有的坑都是從這個版本踩出來的。

| 欄位 | 這個版本的答案 |
|---|---|
| 型態 | 行程 / 待辦提醒 |
| 誰在用 | 自己的家人,5-10 人 |
| bot 做什麼 | 建行程 / 查行程 / 刪行程 / 到點提醒 |
| 主動推播 | 要,這是主功能 |
| 要不要 LLM | **不要**。指令集固定,規則解析實測成功率 95%+,而且家人的輸入不上傳第三方 |
| 技術棧 | Python FastAPI + Supabase Postgres + Render + cron-job.org,全部走免費方案 |
| onboarding | 邀請碼:第一個人建家族當 admin,其他人輸入邀請碼加入 |
| 特別設計 | 兩種建行程方式並存 —— 懶人版一句話直建,新手版(長輩用)打「新增行程」進引導式問答。同一個 bot 不強迫所有人用同一種方式 |

具體用到的套件(供參考,換語言或框架不影響骨架):FastAPI 接 webhook、
SQLAlchemy 加自訂 TypeDecorator 抹平 SQLite 與 Postgres 的 UUID / JSONB
差異、Alembic 管 migration、引導式問答的草稿存在 `conversation_states`
表的 JSONB 欄位。

這個版本的免費額度實測(**單一實例、寫作當時的數字,以各服務官方當下的
方案頁為準**):Supabase free tier 500MB DB + 50K MAU,家族 5-10 人遠低於
上限;Render free tier 每月 750 小時,自動休眠後冷啟動約 30 秒,靠
cron-job.org 每 14 分鐘 ping 一次保活;派送 cron 每分鐘打一次。

**拿它當填法的參考,不要當成你一定要做的東西。**
換成別的型態時,骨架一行都不用改,只有上面這張表的內容不同。

## 我踩過的坑

1. **cron 每分鐘跑,同一筆提醒重複發**:派送端點撈的是「該發但還沒發」
   的項目,發完必須**立刻**標記 —— 這個旗標是避免下一分鐘又撈到同一筆
   的關鍵。
2. **push 部分失敗時不要重試整筆**:只記 log。重試會害已經收到的人
   收第二次。
3. **派送端點裸奔**:cron 打的端點一定要驗 secret header。
4. **本機 / 線上資料庫差異**:用 ORM + 自訂型別轉換抹平 SQLite 與
   Postgres 的差異,「本機測完直接上線」才不會踩雷。
5. **使用者不會用 bot**:不解釋,直接示範 —— 在群組打一句話讓 bot 跳出
   回應,看 1 次就會用。bot 不要寫指令說明書,要讓第一個成功案例自己說話。
6. **官方的自動回覆沒關掉**:bot 回什麼都被罐頭訊息蓋掉,而且看不出
   問題在哪。第 0.5 步第 3 條就是在講這個。

## 紅線與注意

- **secret 不落地**:channel token、channel secret、資料庫連線字串、
  cron secret 一律走環境變數,不硬編碼、不 commit。
  順手建 `.env.example`(只放欄位名不放值)進 repo,`.env` 寫進
  `.gitignore` 並**確認真的被 ignore**
  (`git check-ignore -v .env` 有輸出就對了)。
- **`.env` 不會自己生效**:程式要主動載入它,否則值明明填了卻讀不到,
  看起來像 token 拿錯。
- **驗簽不是選配**:不驗簽的 webhook 等於任何人都能冒充使用者對你的
  bot 說話。做客服、預約、教練這類會存個資的型態尤其不能省。
- **隱私**:接 LLM 前先想清楚哪些內容會被送到第三方。做客服的話,
  使用者可能會在對話裡打訂單號、電話、地址。
- **換平台可行**:Telegram / Discord / Slack 也能做 —— 抽掉 LINE handler
  那段換成對應 API 即可,路由 + 資料庫 + 推播三段通用。
  台灣使用者最常用 LINE,所以原版做 LINE。

## 侷限(誠實告知)

- 規則解析只涵蓋固定格式的句子;句式太自由時會落到 fallback,
  不是萬能的自然語言理解。
- 免費方案的部署平台會自動休眠,冷啟動有延遲 —— 靠外部 ping 保活,
  不適合對延遲極敏感的場景。
- LINE 的推播額度會限制「主動推播型」的規模,做之前先算。
